# Проверка правил дат ВСЕХ памятей на основе церковных календарей

**Цель:** не угадывать \`julian_fixed\` по году 2026, а проверить каждую
карточку празднования по независимым датам 2026, 2027 и 2028 с ссылками
на источники. Каждая карточка остаётся отдельным объектом: сходство имён
не означает одинаковые празднования.

## Запуск

Из \`C:\m\repo\molitvoslov-backend\`:

\`\`\`powershell
& .\venv\Scripts\python.exe manage.py test api.test_calendar_rules_online
& .\venv\Scripts\python.exe manage.py audit_calendar_rules_online --max-new-pages 10
& .\venv\Scripts\python.exe manage.py audit_calendar_rules_online
\`\`\`

**Команда только читает локальную SQLite и веб-страницы**; не изменяет
SQLite, Supabase и JSON. Пробный запуск сохранит первые 10 страниц в кэш,
повторный продолжит без их повторного скачивания. Полный аудит скачивает
**1096 страниц** с Azbyka (365+365+366); перерывы, ошибки сети и повторный
запуск предусмотрены. Минимальная пауза между запросами — 0.5 секунды,
сервер не следует перегружать. При необходимости пауза \`--delay 1\`.

Исходный \`molitvoslov_calendar_database_v4_AUDITED.json\` — если файл
существует в корне Django backend — проверяется на соответствие найденным
правилам. Если файла нет, аудит всё равно работает от локальной SQLite,
но не может выдать статус \`CATALOG_RULE_DIFFERS\`.

## После завершения: reports/calendar_rule_source_audit_2026_2028/

- \`summary.json\`: охват по 3056 карточкам и категориям.
- \`all_3056_rules.csv\`: результат для каждого локального ID, сравнение дат,
  ссылка на карточку Azbyka, существующее и предлагаемое правило.
- \`needs_review.csv\`: только спорные/несопоставленные записи и расхождения.
- \`rule_proposals.json\`: проверяемые предложения \`julian_fixed\` и
  \`easter_offset\` с тремя ссылками на дни; **НЕ автоматическое изменение**.
- \`leap_2028_julian_feb29.json\`: памяти с 13 марта 2028 года, которых
  в невисокосном эталоне 2026 могло не быть.
- \`fetch_errors.csv\`: ошибки загрузки; пока они есть или страницы
  не все скачаны, **финальный отчёт не формируется**.
- \`cache/YYYY/YYYY-MM-DD.json\`: загрузки каждого дня; сохраняются между
  запусками, допускают продолжение без повторных запросов.

## Почему отчёт может сохранять спорные строки

Идентификация через URL святого должна быть однозначной: название группы
может сокращаться, ссылка может быть общей для нескольких памятей, и одна
страница святого может описывать несколько дней празднования. При коллизиях
скрипт **не** назначает дату по имени, а выводит кандидат для проверки.

Три года дают сильные эмпирические свидетельства о неподвижности или
пасхальном смещении, но не заменяют нормативного источника для исключений,
переносов служб, приходских вариантов и совпадений особых праздников.
Сложные воскресные правила (\`weekday_after\`, \`weekday_on_or_after\`)
и уставные исключения требуют отдельной проверки/фиксации основания.

Скрипт не изменяет существующие 2026/2027, а также не делает 2028
готовым к загрузке: после верификации правил потребуется обновить
постоянный каталог и генератор, проверить 29 февраля по юлианскому
календарю, выполнить dry-run 2028, затем отдельно чтения и посты.
