# Заполнение чтений 2027 года в обычном календаре

**Без новой кнопки и без второго интерфейса.** Экран ChurchCalendarScreen уже читает данные из `CalendarDay.readings` и открывает локальную Библию. Команда добавляет отсутствующие `CalendarReading` непосредственно туда.

## На Windows

```powershell
cd C:\m\repo
git fetch origin
git switch -c feature/calendar-2027-readings-native --track origin/feature/calendar-2027-readings-native
cd .\molitvoslov-backend
& .\venv\Scripts\python.exe manage.py fill_calendar_readings --year 2027 --apply
```

Важное: перед `git switch` проверь `git status`. Не сбрасывай несохранённые изменения. Если ветка уже существует локально, используй `git switch feature/calendar-2027-readings-native` и `git pull --ff-only`.

Команда:
- читает уже созданные `CalendarDay` за 2027 год;
- получает опубликованные на конкретную дату чтения `azbyka.ru/days/YYYY-MM-DD`;
- дополняет отсутствующие записи `CalendarReading` по виду, подписи и библейскому диапазону;
- **не удаляет** существующие чтения, не меняет их тексты/порядок/UUID;
- не трогает `CalendarFeast`, главную память, другие памяти, посты, жития и ручные правки;
- делает backup SQLite перед первой записью;
- сохраняет подробный отчёт в `molitvoslov-backend/reports/calendar_readings_2027_fill.json`;
- на дни без опубликованных чтений ничего не выдумывает.

**Только локальная SQLite.** Supabase не изменяется.

Проверить один день до запуска всего года (без записи):

```powershell
& .\venv\Scripts\python.exe manage.py fill_calendar_readings --year 2027 --date 2027-05-02
```

Для записи полного года нужен `--apply`. Команда **дополняет**, но не заменяет ручные записи; возможные расхождения с источником остаются в отчёте.

В блоках "Евангелие", "Апостол", "Ветхий Завет" появятся чтения из `CalendarReading`. Переход в Библию остаётся тем же, что и раньше. Дополнительных элементов интерфейса нет.

## Ограничения

- Некоторые страницы 2027 года на Азбуке веры ещё не содержат опубликованных чтений. Они помечаются как `SOURCE_UNAVAILABLE`. **Отсутствие записи в источнике не означает отсутствие чтения по Уставу.**
- Опубликованное расписание источника — не гарантия учёта всех местных вариантов богослужебной практики. Составные и альтернативные чтения требуют дополнительной сверки.
- Этот этап не означает, что абсолютно все назначения 2027 года уже проверены и внесены. Количество реально дополненных дат нужно смотреть в JSON-отчёте после запуска.
- Результаты прежнего экспериментального генератора с непроверенными кандидатами в базу не импортируются.

## Повторы Евангелия и Апостола: 398 групп с разными подписями

Если старая команда писала `автоматические дубли=0, спорные группы=398`, это значит,
что пары имели одну и ту же ссылку на Писание в пределах одной службы, но разные
подписи (например, `Ряд.` и `Свт.`). Старая версия не удаляла такие записи.

Исправленная версия **объединяет обе подписи на одной карточке**, а не теряет
праздничную/рядовую причину одного чтения. Например:

- `Ин.1:1–17 — Ряд.`
- `Ин.1:1–17 — Свт.`

превращаются в одну запись `Ин.1:1–17 — Ряд.; Свт.`.
Утренняя и вечерняя службы не объединяются с литургией, даже если их стихи совпали.

Всё происходит в обычных `CalendarReading`, не в новом интерфейсе.
Сначала посмотреть план, **ничего не меняя**:

```powershell
cd C:\m\repo\molitvoslov-backend
& .\venv\Scripts\python.exe manage.py deduplicate_calendar_readings --year 2027
```

В отчёте `reports/calendar_reading_coalesce_2027.json` указаны
все прежние подписи, номера записей, диапазоны, порядок и UUID.
Старый отчёт `calendar_reading_duplicates_2027.json` не перезаписывается.

Затем применить объединение:

```powershell
& .\venv\Scripts\python.exe manage.py deduplicate_calendar_readings --year 2027 --apply
```

Перед правками делается резервная копия SQLite. Удаляются только строки с одним
`kind`, той же службой и тем же нормализованным диапазоном книги/стихов.
Памяти святых, посты и другие отрывки не меняются.
Если совмещённая подпись превысила 255 символов или могла изменить тип службы,
такая группа останется для ручной проверки. Повторный запуск ничего не дублирует.

Примечание: число 398 — результат предыдущей версии и **не равно** числу
строк, которое новая версия удалит. Смотри новый dry-run.

## Исправление неполного импорта: 16 января 2027

На странице <https://azbyka.ru/days/2027-01-16> отображаются три
группы чтений:

| Группа | Апостол | Евангелие |
|---|---|---|
| Субботы | 1Тим.3:14–4:5 | Мф.3:1–11 |
| Мч. | 2Тим.2:1–10 | Мф.10:16–22 |
| Рядовое | 1Сол.5:14–23 | Лк.17:3–10 |

Старый `extract_readings_text()` брал **первый** HTML-абзац и терял
четыре отрывка из двух последующих групп.

Исправлено: все абзацы раздела собираются в одно расписание,
а объясняющий текст после списка не импортируется как служба.
Тест проверяет шесть чтений и безопасный `--merge` из двух до шести.

Обновить существующие записи **без перезаписи святых, постов, житий
или уже внесённых чтений**:

```powershell
cd C:\m\repo
git pull --ff-only
cd .\molitvoslov-backend
& .\venv\Scripts\python.exe manage.py test api.test_azbyka_calendar_readings
& .\venv\Scripts\python.exe manage.py fill_calendar_readings --year 2027 --date 2027-01-16 --apply
```

В результате за 16 января должно быть три Евангелия и три Апостола
(если до этого в локальной базе была только одна пара, добавится 4 строки).

После проверки одной даты запустить `fill_calendar_readings --year 2027 --apply`
для всего года: повторный запуск не создаёт дублей. В обычном
`ChurchCalendarScreen` теперь видны **все** чтения дня, без
искусственного ограничения первым/вторым чтением.

Если после повторного импорта в приложении отображается прежняя пара,
убедитесь, что эмулятор подключён к локальному Django на `10.0.2.2:8000`,
перезапустите приложение, проверьте дневной ответ
`/api/calendar/day/?date=2027-01-16&lang=ru`.
Существующий офлайн-кэш может временно показывать старые данные,
когда локальный backend не отвечает.

## Завершение пяти дат Великого канона

При проверке всего 2027 года прежний парсер мог выдать пять
`SOURCE_UNAVAILABLE`:

- 15, 16, 17, 18 марта — первые четыре дня первой седмицы Великого поста;
- 14 апреля — среда пятой седмицы Великого поста.

Это не сетевые ошибки и не ошибка регулярного выражения.
На этих пяти страницах `azbyka.ru/days/YYYY-MM-DD` в блоке
«Чтения Священного Писания» стоит ссылка «Великий канон Андрея
Критского», а обычные библейские диапазоны не указаны.

Для **этих конкретных пяти дат** добавлен проверенный запасной источник
Orthocal в режиме Slavic + Julian. Там опубликованы 3 паремии в день:

| Дата | На 6-м часе | На вечерне |
| --- | --- | --- |
| 2027-03-15 | Ис.1:1–20 | Быт.1:1–13; Притч.1:1–20 |
| 2027-03-16 | Ис.1:19–2:3 | Быт.1:14–23; Притч.1:20–33 |
| 2027-03-17 | Ис.2:3–11 | Быт.1:24–2:3; Притч.2:1–22 |
| 2027-03-18 | Ис.2:11–21 | Быт.2:4–19; Притч.3:1–18 |
| 2027-04-14 | Ис.41:4–14 | Быт.17:1–9; Притч.15:20–16:9 |

Источники по датам (прямые ссылки):

- https://orthocal.info/readings/slavic/julian/2027/3/15/
- https://orthocal.info/readings/slavic/julian/2027/3/16/
- https://orthocal.info/readings/slavic/julian/2027/3/17/
- https://orthocal.info/readings/slavic/julian/2027/3/18/
- https://orthocal.info/readings/slavic/julian/2027/4/14/

Их нельзя выдавать за чтения, опубликованные на Азбуке: источник
указан отдельно в выводе импорта. Если Азбука в будущем добавит
ссылки на Писание, **её записи будут иметь приоритет**.

Проверить без записи и без обхода остальных 360 дней:

```powershell
cd C:\m\repo\molitvoslov-backend
& .\venv\Scripts\python.exe manage.py fill_calendar_readings --year 2027 --special-2027
```

После успешной проверки внести только недостающие записи:

```powershell
& .\venv\Scripts\python.exe manage.py fill_calendar_readings --year 2027 --special-2027 --apply
```

Это стандартный `--merge` со штатными `CalendarReading(kind="old_testament")`,
автоматическим backup SQLite перед первой записью. Существующие чтения
и прочие данные дня сохраняются. Повторный запуск идемпотентен.
Новый диагностический файл `reports/calendar_readings_2027_special_5.json`
не перезаписывает прежний годовой отчёт `calendar_readings_2027_fill.json`.
